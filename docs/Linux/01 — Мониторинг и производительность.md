# Мониторинг и производительность в Linux

## Load Average (LA)

**Load Average** — среднее количество процессов, находящихся в очереди на выполнение за последние 1, 5 и 15 минут. Выводится тремя числами: `0.78 1.48 1.10`.

### Как интерпретировать

- Значение LA нужно **делить на количество логических ядер** процессора.
- LA = 4.0 при 4 ядрах = 100% нагрузка (норма).
- LA = 4.0 при 1 ядре = перегрузка в 4 раза.
- LA < количества ядер — система справляется.
- LA >> количества ядер — проблема: очередь растёт быстрее, чем обрабатывается.

### Что влияет на LA (и почему высокий LA не всегда проблема)

LA учитывает не только CPU, но и:
- **CPU-bound** задачи (процессор занят)
- **I/O-wait** задачи (процесс ждёт диска/сети — состояние `D`)

Поэтому высокий LA может быть из-за медленного диска, а CPU при этом свободен и SSH отзывается нормально.

### Технологии, влияющие на расчёт

- **Hyper-Threading** — одно физическое ядро делится на 2 логических, удваивая пропускную способность
- **Turbo Boost** — процессор разгоняется выше номинала, задачи обрабатываются быстрее

### Как посмотреть

```bash
uptime           # показывает LA за 1/5/15 минут
cat /proc/loadavg
top              # первая строка
htop             # в шапке
```

## Утилита top

`top` — интерактивный монитор процессов в реальном времени.

### Разбор вывода

```
top - 21:29:24 up 14:18,  1 user,  load average: 0.78, 1.48, 1.10
Tasks: 277 total,   3 running, 274 sleeping,   0 stopped,   0 zombie
%Cpu(s): 12.4 us,  2.5 sy,  0.1 ni, 84.8 id,  0.1 wa,  0.0 hi,  0.1 si,  0.0 st
```

**Поля CPU:**

| Поле | Название | Описание |
|------|----------|----------|
| `us` | user | Процессорное время пользовательских процессов |
| `sy` | system | Процессорное время ядра |
| `ni` | nice | Процессы с изменённым приоритетом |
| `id` | idle | Простой — свободные ресурсы |
| `wa` | iowait | Ожидание I/O (диск, сеть) — CPU простаивает, ждёт диск |
| `hi` | hardware irq | Аппаратные прерывания |
| `si` | software irq | Программные прерывания |
| `st` | steal | «Украдено» гипервизором (виртуалки) |

**Состояния процессов в Tasks:**
- `running` — выполняется прямо сейчас
- `sleeping` — ждёт событие/сигнал
- `stopped` — остановлен сигналом SIGSTOP
- `zombie` — завершился, но ещё в таблице процессов

### Горячие клавиши top

| Клавиша | Действие |
|---------|----------|
| `1` | Показать нагрузку на каждое ядро отдельно |
| `c` | Показать полную команду запуска процесса |
| `M` | Сортировка по памяти |
| `P` | Сортировка по CPU |
| `k` | Убить процесс (ввести PID) |
| `q` | Выход |
| `H` | Показать потоки (threads) |
| `u` | Фильтр по пользователю |

### htop vs top

`htop` — улучшенная версия top: цветной вывод, поддержка мыши, дерево процессов (`F5`), поиск (`F3`), Kill (`F9`).

### Что делать если wa высокий

Высокий `wa` (больше 10-20%) — CPU не занят, он просто **стоит и ждёт** пока диск ответит. Это сигнал: проблема в дисковой подсистеме.

**Порядок расследования:**

```bash
# Шаг 1: убедиться что проблема в диске
top   # смотришь wa

# Шаг 2: какой диск перегружен и насколько
iostat -xtc 1
# смотришь %util (близко к 100% — диск еле тянет)
# и await (среднее время ожидания ответа, норма < 10-20ms)

# Шаг 3: кто конкретно грузит диск
iotop
# видишь процесс, который больше всех читает/пишет

# Шаг 4: что это за процесс и почему
ls -la /proc/PID/fd     # что за файлы открыты
lsof -p PID             # то же самое, удобнее
```

**Типичные виновники:**
- БД с неоптимальными запросами (полный скан таблицы)
- Логирование в debug-режиме (пишет гигабайты)
- Бэкап запустился в пиковое время
- Физически деградирующий диск (`dmesg | grep -i error`)

Только после диагностики — решение. "Заменить диск" — последний вариант, не первый.

## Мониторинг дисков: iostat

`iostat` входит в пакет `sysstat`.

```bash
# Установка
apt install sysstat   # Debian/Ubuntu
yum install sysstat   # RHEL/CentOS

# Использование
iostat -xtc 1 5    # расширенный вывод, каждую секунду, 5 итераций
```

### Ключевые поля iostat

| Поле | Описание |
|------|----------|
| `%util` | % времени, когда диск был занят. Близко к 100% — диск перегружен |
| `await` | Среднее время ожидания I/O операции (мс). Норма < 10-20 мс |
| `r/s`, `w/s` | Операций чтения/записи в секунду |
| `rkB/s`, `wkB/s` | КБ чтения/записи в секунду |
| `svctm` | Среднее время обслуживания запроса |

### Другие инструменты для мониторинга дисков

```bash
iotop          # интерактивный мониторинг I/O по процессам
df -h          # использование дискового пространства
du -sh /path   # размер директории
lsblk          # структура блочных устройств
```

## Мониторинг памяти: free

```bash
free -m     # в мегабайтах
free -h     # в человекочитаемом формате
```

### Пример вывода и расшифровка

```
              total    used    free   shared  buff/cache  available
Mem:           6930    3598     843      183        2489       2919
Swap:         15999       4   15995
```

| Поле | Описание |
|------|----------|
| `total` | Вся физическая RAM |
| `used` | `total - free - buff/cache` |
| `free` | Полностью свободная, неиспользуемая память |
| `shared` | tmpfs и разделяемая память |
| `buff/cache` | Буферы ядра + кэш файлов |
| `available` | Реально доступно для новых приложений (free + освобождаемый кэш) |

> **Важно:** `available` > `free`, потому что ОС может отдать часть `buff/cache` под новые процессы.

### Формула

```
available ≈ free + buff/cache (часть, которую можно освободить)
```

### Swap

Раздел подкачки — место на диске, куда ядро вытесняет неиспользуемые страницы памяти. Использование swap не всегда плохо: ядро само решает, что вытеснять.

Настройка агрессивности swap:
```bash
cat /proc/sys/vm/swappiness   # значение 0-100, обычно 60
sysctl vm.swappiness=10       # меньше — реже использует swap
```

## Комплексный мониторинг: vmstat

```bash
vmstat 1 5    # каждую секунду, 5 итераций
```

Показывает: процессы, память, swap, I/O, прерывания, CPU — в одной строке.

## Чеклист при расследовании проблем с производительностью

```bash
# 1. Смотрим общую картину
top / htop

# 2. Проверяем LA и ядра
uptime
nproc

# 3. Смотрим I/O (диски)
iostat -xtc 1

# 4. Смотрим память
free -m
vmstat 1

# 5. Смотрим сеть
ss -s
iftop / nethogs

# 6. Ищем виновника
iotop          # кто грузит диск
ps aux --sort=-%cpu | head -10   # топ по CPU
ps aux --sort=-%mem | head -10   # топ по памяти
```
